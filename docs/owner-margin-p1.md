# Halk Büfe Selinus — локальный расчёт маржинального дохода (P1)

## Назначение
Адрес инструмента: `/owner/?lang=ru`. Он работает **только на данных, которые владелец сам выбирает на доверенном компьютере**.

**Это не защищённый логином личный кабинет, не касса, не сервис платежей и не облачная аналитика.** Страница размещена публично на GitHub Pages, но не имеет доступа к финансовым файлам, пока человек сам не выберет их на своём устройстве. Не размещайте поставщиков, реальные затраты, кассовые выгрузки, личные данные и пароли в репозитории или общедоступных URL. Для защищённого онлайн-кабинета потребуется отдельная серверная архитектура с аутентификацией, правами доступа и журналами аудита.

Страница не содержит сторонних шрифтов, аналитических скриптов, форм отправки, API-запросов или локального постоянного хранения импортированных данных. CSP ограничивает соединения `connect-src 'none'`. Данные читаются через браузерный File API и находятся в памяти страницы. Обновление/закрытие страницы удаляет эти данные из приложения. Не считайте это защитой от недоверенных расширений браузера или скомпрометированного устройства.

## Как пользоваться
1. Откройте `https://safal207.github.io/halk-bufe-selinus/owner/?lang=ru` на доверенном устройстве.
2. Нажмите «Скачать пустой шаблон CSV» для затрат. В нём перечислены 44 публичных `item_id` из меню; **все суммы пустые**, никаких выдуманных затрат.
3. Заполните по каждому SKU проверенные переменные расходы в TRY, используя точку как десятичный разделитель. Для себестоимости считайте порцию блюда, упаковку и прочие переменные расходы.
4. Выгрузите из POS **все оплаченные строки чека** за анализируемый период. Если за период были возвраты, включите в файл исходные оплаченные строки и относящиеся к ним возвраты. Без исходных продаж возвращённые строки будут признаны ошибкой.
5. Приведите выгрузку к указанным ниже заголовкам и импортируйте оба CSV. Результаты обновятся на экране, но **не будут отправлены на сервер**.
6. Проверяйте предупреждения. Если хотя бы одна оплаченная позиция не имеет себестоимости, есть некорректные чеки, конфликт `void` или неподтверждённый возврат, общие маржинальный доход и процент маржи намеренно скрываются.

### CSV затрат
Первая строка (строго такие имена колонок):

```csv
item_id,ingredients_try,packaging_try,other_variable_try
```

`item_id` — точный идентификатор из `menu.js`. Остальные поля — **неотрицательные** значения в турецких лирах за одну проданную порцию, с точкой и максимум двумя знаками после неё. Они **не** являются примерной себестоимостью из публичного меню. Стоимость ингредиентов, упаковки и дополнительных переменных расходов должна быть предоставлена владельцем из бухгалтерии/техкарты.

### CSV строк POS
Первая строка:

```csv
line_id,receipt_id,status,item_id,quantity,net_unit_revenue_try
```

- `line_id` — уникальный идентификатор строки/операции POS, включая возвраты, **без повторов**.
- `receipt_id` — номер реального чека; у нескольких блюд в одном чеке номер одинаковый.
- `status` — `paid`, `refunded`, `void` или `pending`.
- `item_id` — соответствующий идентификатор из меню. Для POS с другими SKU необходим отдельный проверенный справочник соответствий; не подменяйте позиции угадыванием.
- `quantity` — положительное целое от 1 до 999. Для возвратов используйте положительную величину со статусом `refunded`.
- `net_unit_revenue_try` — фактическая **чистая выручка за единицу** после скидок и без собираемых косвенных налогов, а не публичная цена сайта. Валюта — TRY, максимум два десятичных знака.

CSV допускает запятые и точку с запятой как разделители, UTF-8 BOM и кавычки. Ограничения: до 1,5 МБ на файл и максимум 20 000 строк. Данные меньших/больших единиц или с ошибочным форматом необходимо сначала преобразовать **в частной учётной системе**.

## Определения метрик

`net_sales` = сумма(`paid.quantity × paid.net_unit_revenue`) − сумма(`refunded.quantity × refunded.net_unit_revenue`) для корректных, сопоставленных чеков.

`unit_variable_cost` = `ingredients_try + packaging_try + other_variable_try`.

`contribution` = `net_sales − net_units × unit_variable_cost`, где `net_units = paid.quantity − refunded.quantity`.

`margin_percent` = `contribution / net_sales × 100` только при положительной выручке и полной достоверности переменных затрат.

`paid_receipts` — количество **чеков с положительным нетто**, а не количество посетителей сайта или подготовленных QR-кодов. Не является доказательством подлинности загруженного CSV.

При некорректных строках POS или конфликте статусов **скрываются также общая выручка и число оплаченных чеков**, чтобы частичный подсчёт не выглядел подтверждённым итогом.

Если чек содержит противоречивые статусы `void` и `paid`/`refunded`, такой чек целиком исключается и показывается предупреждение. Если возврат больше исходной продажи, соответствующая позиция исключается. Повторные `line_id` отмечаются; `pending` и `void` не учитываются как продажи. Период нужно определять на стороне POS — в демо нет календаря, времени операций или внешней проверки.

**Маржинальный доход не равен чистой прибыли.** Постоянные зарплаты, аренда, налоги и другие не включённые затраты вычитаются отдельно.

## Что ещё не реализовано
- Закрытый owner/cashier аккаунт, роли, MFA, серверная база или оплата.
- Автоматическая интеграция с действующей кассовой программой.
- Подтверждение `purchase` по подготовленному сайтом номеру заказа.
- Хранение исторических периодов, сезонные тренды, уплаченные налоги, зарплаты и обороты склада.
- Валидирование исходных документов через POS API или подпись кассы.

### Рекомендуемый следующий этап (P2)
Прежде чем включать реальные отчёты владельца онлайн, определить поставщика POS и формат его экспортных отчётов. После этого проектировать **авторизованный backend**: серверная цена и SKU, `external_receipt_id`, жизненный цикл оплаты/отмены/возврата, ограничения доступа, уникальность операций, журнал аудита и сверка заказов с POS. Данные по себестоимости — в закрытой базе с разграничением прав; на публичный GitHub Pages их помещать нельзя.

## Регрессионная проверка
- `npm test` — парсинг CSV, безопасность целочисленной арифметики, зачёт только оплаченных строк, вычитание возвратов, дедупликация, конфликты `void`, пропуски себестоимости и отсутствие сетевых соединений.
- `npm run test:e2e` — загрузка файлов в браузере, RU/TR, сброс данных, экран 320–1440 px, отсутствие публичного прибыльного виджета в клиентском меню. В GitHub Actions те же проверки выполняются в Chromium, Firefox, WebKit и Microsoft Edge.
